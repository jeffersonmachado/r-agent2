# Current Flow Runtime Mapping

## Frontend Authoring Boundaries

### Editor format (Rete JSON)
- Primary editor state is generated by `frontend/src/editor/createEditor.js` via `editor.toJSON()`.
- Validation in editor UI is split between:
  - Local structural validation: `frontend/src/editor/flowValidator.js`
  - Schema-level node validation: `frontend/src/editor/validation/runFlowValidation.ts`
  - Backend flow validation via API: orchestrated in `frontend/src/state/editorStore.jsx`

### Editor-to-engine conversion
- Conversion entrypoint: `frontend/src/engine-mapper/engineMapper.js`
  - `reteJsonToEngineFlow(reteJson, meta)`
  - `engineFlowToReteJson(flow)`
- This mapper is explicitly format conversion only (no deep business semantics).

## Backend Runtime Boundaries

### Runtime input model currently in production
- Runtime consumes `FlowDefinition` (legacy engine format), not BPMN directly.
- Key contracts are documented in `engine/flowTypes.js`.

### Compilation and execution path
- Compile/caching:
  - `engine/compileFlow.js`
  - `engine/compiledFlowCache.js`
- Single-step deterministic execution:
  - `engine/executeStep.js`
  - delegates to runner/registry handlers.

### Runtime decision points
- Main message path:
  - `api/services/messageProcessor.js`
  - builds registry, obtains flow, compiles via `getOrCompileFlow`, executes via `executeStep`.
- Simulation path:
  - `engine/flowSimulation.js` (mock AI provider + executeStep loop with replay).

## Where Validation, Serialization, Simulation, Execution Live

- Serialization:
  - `frontend/src/engine-mapper/engineMapper.js`
  - `frontend/src/bpmn/engineFlowToBpmnXml.js`
  - `frontend/src/bpmn/bpmnXmlToEngineFlow.js`
- Validation:
  - Editor local: `frontend/src/editor/flowValidator.js`
  - Backend/engine validation API path: `frontend/src/state/editorStore.jsx` + API route
  - BPMN compatibility validation: `frontend/src/bpmn/validateBpmnCompatibility.js`
- Simulation:
  - `engine/flowSimulation.js`
- Execution:
  - `api/services/messageProcessor.js` + `engine/executeStep.js`

## Integration Risks Found

1. Mapper/runtime coupling on legacy node types
- Risk: runtime handlers are keyed by legacy types (`start`, `router`, `message`, etc.).
- Impact: introducing new authoring formats directly in runtime would be high-risk.

2. Validation fragmentation
- Local, backend, and BPMN validations are separate pipelines.
- Impact: semantic issues can slip between layers unless normalized first.

3. Runtime entry still expects legacy `FlowDefinition`
- Impact: any canonical adoption must include an adapter layer first.

4. Type-level semantic loss on cross-format conversion
- Example: routing conditions and fallback semantics can degrade when serialized between formats.

## Canonical Insertion Point (Defined)

The canonical insertion is now explicitly:

`Rete JSON / BPMN / AI Prompt -> CanonicalProcessDefinition -> Canonical Compiler+Validator -> Legacy Engine Adapter -> executeStep`

This keeps the existing editor/runtime behavior intact while enabling incremental migration.
